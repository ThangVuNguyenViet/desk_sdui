# desk_sdui_generator — augmentation-based codegen

**Goal:** Replace `.sdui.g.dart` part files with Dart 3.6 augmentation libraries. Screen authors stop needing `part 'foo.sdui.g.dart';` directives at the top of every `@Screen`-bearing file; codegen instead emits `augment library;` files that the analyzer + runtime pick up natively.

**Prereq:** `.plans/desk-sdui-analyzer-8.md` merged. Augmentation support in analyzer 13 is required.

**Architecture:**
- Builder emits `foo.sdui.g.dart` as an **augmentation library** (`augment library 'foo.dart';` header) rather than a part file.
- The author file declares `import augment 'foo.sdui.g.dart';` (one line; replaces `part 'foo.sdui.g.dart';`).
- The augmentation library declares augmented top-level functions / classes via `augment` keyword.
- The build_runner builder configuration changes: `Builder` emits to a new extension `.sdui.aug.dart` (or keeps `.sdui.g.dart` if the augmentation form is back-compat with the part shape — verify experimentally).
- The per-screen registration file (`foo.sdui_reg.g.dart`) stays as-is — it's a standalone library, not a part.

**Why:** Part files leak two pieces of ceremony into the consumer's source — the `part` directive and the awareness that codegen exists at all. Augmentations let the generator add to a screen's public surface without the consumer's file needing to acknowledge the binding mechanism. Also: parts can't have their own imports (the cue example plan hit this and had to spin up a separate `.sdui_reg.g.dart`), augmentations can.

**Tech stack:** `analyzer ^13`, `build ^4`, `source_gen ^4`, dart-lang augmentations (Dart 3.6+).

**Repo:** `/Users/vietthangvunguyen/Workspace/dart_desk_workspace/desk_sdui/`

**Acceptance:**
1. `desk_sdui_demo` no longer contains any `part '*.sdui.g.dart';` directives in screen sources.
2. Each screen source has `import augment '<name>.sdui.g.dart';` at the top.
3. `flutter run -d chrome` renders the demo identically to pre-change behavior.
4. All generator + demo tests pass.

## Open questions to resolve in Task 1 spike

These determine whether this plan ships at all:

1. Do augmentations + `build_runner` + `flutter run` actually compose without an experiment flag in current stable Dart? If a flag is needed, what's the rollout story for consumers?
2. Can an augmentation library carry its own imports (fixing the parts-can't-import limitation)? If yes, the two-file split collapses (Task 3 step 3 + Task 4 step 1).
3. Are there any IDE / `dart analyze` complaints unique to augmentations (e.g. golden file regen quirks, hover-doc behavior)?

If the spike answers any of these as a hard no, STOP and report — the plan needs revision.

## Out of scope

- Augmentation of `@Screen` classes (the screens are top-level functions today; the augmentation form for *functions* is enough). If/when screens become classes, the per-class augmentation form is a follow-up.
- Migrating consumer-owned files outside `desk_sdui_demo`. Real consumers update on their own schedule.
